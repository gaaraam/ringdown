# 고객사 Pack 온보딩

가가클리닉 예약 안내 팩을 추가하며 확인한 절차다. 현재 실행 범위는 RuleBrain·mock 시뮬레이션이다. 실제 발신, 업무 API, SMS, 인증을 연결한 운영 서비스로 간주하지 않는다. 수치와 제약은 [M5 실험 기록](experiments/2026-11-m5-onboarding.md)에 남겼다.

## 고객에게 먼저 물을 것

- 이번 전화 한 통의 목적은 무엇인가? 예약 유지도 성공인가, 변경·취소만 성공인가? 고객이 원하지 않으면 어디서 멈추는가?
- 누가 전화를 받을 수 있는가? 본인·대리인·미성년자별 확인 항목과 실패 절차는 무엇인가? 확인 전 읽어도 되는 정보와 숨겨야 하는 정보를 구분한다.
- 예약의 원장은 어느 시스템인가? 다음 예약이 여러 개거나 없을 때, 이미 취소됐을 때, 조회 후 다른 창구에서 바뀌었을 때 어떻게 하는가?
- 변경 가능한 시간을 누가 계산하는가? 시간대·마감·휴진·중복 예약·슬롯 만료를 누가 검사하는가?
- 변경/취소 동의 때 반드시 읽을 내용은 무엇인가? 취소 수수료처럼 금전 조건이 있다면 승인된 원문과 적용 범위를 받는다.
- 답하면 안 되는 질문, 상담원 큐, 운영 시간, 콜백 기한, 결과 불명 작업의 담당자는 누구인가?
- 정상·장애 시 허용 종료와 중단 기준을 정한다. 실제 고객 분포 자료가 없다면 합성 페르소나를 실제 전환율 예측에 쓰지 않는다.

클리닉 예시는 이름 확인 후 “처음 접수하신 경로”를 묻는다. 모든 가상 대상의 경로가 방문 접수인 고정 집단이다. 두 번째 질문에 “네”만 답하면 이관하고 예약을 조회하지 않는다. 이것은 단계 분리의 검증이며, 개별 환자에 대한 안전한 인증 방식은 아니다. [#20](https://github.com/gaaraam/ringdown/issues/20)이 해결되고 고객이 인증 절차를 승인하기 전 실제 환자에게 적용하지 않는다.

## 업무 API 계약을 먼저 맞추기

| 항목 | 고객 시스템 담당자와 확인할 내용 | 통과 증거 |
|---|---|---|
| 인증 | 읽기·변경·취소 권한 분리, 토큰 만료/갱신, 서버 측 대상 접근 검사. 비밀값은 저장소에 넣지 않고 환경변수 이름만 기록 | sandbox에서 정상/만료/권한 부족 요청 결과 |
| 멱등성 | 요청마다 논리 작업 ID를 만들고 재시도 시 같은 키 사용. 보관 기간, 같은 키·다른 본문의 오류, 중복 취소 의미 합의 | 응답을 잃은 뒤 재시도해 실제 쓰기 한 번, 동일 결과 |
| 시간 제한 | 도구별 timeout·최대 재시도·전체 통화 시간 합의. 클리닉 조회 1500ms/재시도 2회, 쓰기 2500ms/1회는 시뮬레이션 값 | 지연/무응답/늦은 성공에서도 침묵과 이중 처리 없음 |
| 오류 의미 | 4xx/5xx/미연결/timeout 구별. 요청 거부와 적용 여부 불명을 구분. 예약 충돌·대상 없음·이미 취소됨 응답 정의 | 실패 응답별 통화 결과와 후속 처리 담당자 표 |
| 결과 조회 | timeout을 취소 성공이나 실패로 단정하지 않는다. 같은 작업 키로 실제 상태를 확인할 API 필요 | 확인 필요 항목과 원장 상태 대조 |
| sandbox | 운영 데이터와 인증 분리, 합성 데이터, 초기화 방법, 실패 주입, 데이터 보존 기한 | 정상·느림·간헐 오류·전면 장애·응답 유실 재현 |

현재 `http-json`은 설정 스키마만 있으며 `runCall`은 mock 이외 연결을 거부한다. `jacks.yaml`의 타입만 바꾸면 실제 연동된다고 안내하지 않는다. 의료 시스템의 인증, 동적 슬롯, 동시성 처리는 별도 구현·검증 대상이다. 클리닉 mock의 `appointmentLabel`은 최초 예약 안내 스냅샷이고, 변경 후 상태는 `appointmentTime`과 `resolution`으로 확인한다. mock 상태는 통화마다 초기화되므로 캠페인 간 예약 원장 동기화를 증명하지 않는다.

## 한국 아웃바운드 정책을 법무팀과 확인하기

아래는 고객 법무팀의 확인 항목이며 법률 자문이나 적법성 판정이 아니다. 2026-11-17에 국가법령정보센터 조문을 확인했으며, 실제 출시일의 시행 법령·업종별 규정을 다시 검토한다.

- 예약 안내에 광고나 추가 서비스 권유가 섞이는지 분류받는다. 광고성 정보에 해당한다면 사전 동의, 예외의 적용 조건, 발신자 표시, 수신 거부 방법, 야간 별도 동의 등을 고객 법무팀이 확인하게 한다. 팩의 평일 09:00~18:00은 이 데모의 자체 정책이며 법적 허용 시간의 판정이 아니다. [정보통신망법 제50조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1030434421)
- 연락처 취득·예약 안내 이용·위탁 처리의 근거, 목적 변경, 보관 기간과 삭제, 접근권한, 로그 마스킹을 확인한다. 예약/건강 관련 정보의 민감정보 해당 여부와 처리 근거를 따로 검토받는다. [개인정보 보호법 제23조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1033813019)
- AI 상담원·통화 목적·기록 사실 고지 문구를 승인받는다. 녹음/전사/품질 분석의 근거와 필요한 동의·거절 시 처리, 보존 기간을 구분해서 확인한다. 고지 한 문장만으로 모든 요건이 충족된다고 가정하지 않는다.
- 본인 확인 전 예약 날짜·진료 내용을 노출하지 않는지, 대리인과 미성년자 응대, 의료 질문의 이관 범위, 업무 수탁자와 국외 이전 여부를 확인한다. 주민번호나 상세 의료 이력을 확인용 질문으로 임의 도입하지 않는다.
- 통화 가능 시간·휴일·일일 연락 횟수·수신 거부 동기화·콜백 연락 근거를 확인한다. 현재 엔진은 `callWindow`를 집행하지 않는다([#23](https://github.com/gaaraam/ringdown/issues/23)). 실제 발신 전 별도 자격 검사와 통합 테스트가 필요하다.

## 합의한 내용을 파일로 옮기기

| 파일 | 담을 내용 | 클리닉에서 한 선택 |
|---|---|---|
| `pack.yaml` | 목적, 업무 상태 성공 조건, 정책, 단계/전이, 도구 권한, 동의, 멱등성, 실패 처리, 게이트 | 이름 → 접수 경로 → 예약 조회 → 유지/변경/취소. 변경·취소 각각 별도 동의 단계 |
| `jacks.yaml` | 연결 종류, 환경변수 참조 | mock 하나, 실제 비밀값 없음 |
| `mock.yaml` | 읽기/쓰기 경로와 초기 업무 데이터 | 이름과 예약 컬렉션 분리, `DEMO-*` 식별자, 연락처·주민번호·생년월일 없음 |
| `personas.yaml` | 30명 행동·인내심·협조성·버릇 | 수락 16, 짧으면 수락 4, 질문 후 수락 4, 거절 2, 수신 거부 1, 이관 1, 바쁨 2 |
| `kb/*.md` | 승인된 안내와 답변 범위 | 예약 절차만 안내. 의료 판단·복약 조언을 담지 않음 |
| `baselines/` | CLI가 만든 비교 기준 | 현 CLI는 루트 경로를 요구하므로 팩 내 원본과 루트 사본을 동일성 검사 |
| `scenarios/regressions/` | 놓치면 안 되는 장애 통화 | CLI pin으로 변경/취소 lost-ack을 고정하고 팩 테스트에서 재생 |

템플릿 길이 검사는 fact 값을 짧게 추정한다. 따라서 긴 이름·날짜를 실제로 치환한 문장과 고정 고지도 발화 상한 안인지 확인한다. 금지 표현 검사는 문자열 규칙이므로 모든 의료 조언을 의미적으로 판별하는 장치는 아니다. 승인된 예약 문구만 사용하고 의료 키워드/일반 질문은 이관한다.

동적 응답 비교나 API 시간 목록을 YAML 키워드로 가장하지 않는다. 표현할 수 없는 요구는 [엔진 이슈](experiments/2026-11-m5-onboarding.md#엔진에-남긴-과제)에 적고 고객에게 시뮬레이션의 제약을 설명한다.

## 출시 전 검증 게이트

```sh
npm ci
npm run validate
npm run soundcheck -- --pack packs/gaga-clinic --brain rule --faults all --seeds 3
npm run soundcheck -- --pack packs/gaga-clinic --brain rule --faults all --seeds 3 --baseline
npm run ci
git diff main --stat -- src web scripts
```

마지막 출력은 비어 있어야 한다. 기존 두 팩·기준선도 바뀌지 않아야 한다. 테스트와 기준선의 통과는 모의 온보딩 승인 조건이며 실제 전화 출시 승인은 아니다.

클리닉 게이트는 `goal_rate >= 0.20`, `acceptable_rate >= 0.95`, `barge_in_rate <= 0.15`, `long_call_rate <= 0.05`, `policy_violations == 0`, `dead_air_incidents == 0`이다. 450통화에서 목표 성공 0.2867, Wilson 95% 구간 0.2468~0.3301로 0.20보다 여유가 있다. 유지도 거절·장애도 분모에서 빼지 않았다. 허용률 1.0은 콜백·이관·거절을 허용하기 때문이며 업무 성공률과 구분한다. 고객마다 표본과 업무 목표가 다르므로 이 수치를 그대로 복사하지 않는다.

게이트는 점추정으로 판정한다. smoke는 한 시드의 무관용 게이트만 검사하므로 전체 3시드 검증을 생략하지 않는다. 목표 성공을 높이기 위해 기존 예약 상태를 처음부터 성공으로 두거나, 유지를 의미 없는 쓰기로 바꾸지 않는다. 두 쓰기 모두 동의 거절·수신 거부·의료 질문에서 쓰기 0회, lost-ack에서 같은 키 재사용·실제 반영 1회·확인 작업 등록을 별도로 확인한다.

## 콘솔에서 소규모 검증 후 확대하기

1. 임시 또는 전용 `DATA_DIR`로 `npm run play`를 실행한다. 하나의 디렉터리에는 서버 하나만 쓴다. 데모 중에도 선언한 통화 시간 안에 실행한다.
2. Playground에서 새 Pack을 선택해 직접 이름 확인 → 추가 사실 → 유지/두 시간 선택/취소를 재생한다. 최종 동의 전에는 쓰기가 없어야 한다. 자동 페르소나는 정답과 단계를 아는 장치이므로 직접 입력 검사도 한다.
3. 캠페인에서 먼저 일부 대상과 `clean`으로 흐름을 확인한다. 이후 30명 `lost-ack`, `down` 등으로 확대한다. 운영 현황은 캠페인 필터를 걸어 다른 팩 결과와 섞지 않는다.
4. 결과보다 후속 처리함을 먼저 점검한다. 확인 필요는 멱등 키와 저장된 쓰기·업무 상태를 대조한 뒤 안내하고, 담당자·메모·완료 상태를 저장한다. 목표 달성 통화에도 확인 필요가 남을 수 있다. 현재 자동 SMS·상담원 큐 연결·콜백 발신은 하지 않는다.
5. 잘못된 본인 확인, 동의 없는 쓰기, 의료 조언, 이중 반영이 한 건이라도 보이면 추가 캠페인을 중지하고 trace를 고정한다. 실제 운영 전 별도의 고객 법무·보안·업무 담당자 검토와 실 API sandbox 검증이 필요하다.
6. 버전별로 목표/허용률, 입력 이관, API 오류, 미처리 후속 작업 수와 경과 시간을 확인한다. 담당자별 처리 기한이나 자동 중단은 현재 콘솔 기능이 아니므로 운영 책임과 점검 주기를 따로 정한다.

캠페인은 시뮬레이션이며 30명을 실행해도 전화가 나가지 않는다. 로컬 콘솔에는 운영용 인증·권한이 없으므로 실제 고객 데이터를 올리거나 외부에 노출하지 않는다.
